# 运行状态回写设计

## 问题

Codex 任务创建时会在 SQLite 中写入 `PENDING`，但用户加载并成功校验 `result.json` 后，应用只更新当前实验 checkpoint，没有更新历史运行记录。因此历史运行页面会永久显示 `PENDING`，与实际结果不一致。

## 目标

- Stage 1/Stage 2 结果成功加载并校验后，准确更新对应历史运行记录。
- 校验失败时记录 `FAIL`，保留失败原因供历史排查。
- 只更新当前任务对应的 `run_id` 与阶段，不影响同一 KP 的其他运行。
- 保留 `.kg_tasks/pending/` 目录结构，不移动任务文件。

## 方案

在 `repositories/run_store.py` 增加按 `run_id` 和 `stage` 更新运行状态的方法，支持更新 `status`、解析结果和校验结果。加载 Stage 1/Stage 2 结果成功后调用该方法，分别写入完成状态；解析或验证异常时写入失败状态。API 自动模式也在成功完成或失败时同步写入历史记录，避免两种运行模式行为不一致。

状态约定：任务创建为 `PENDING`，Stage 1 成功为 `STAGE1_COMPLETED`，Stage 2 成功为 `COMPLETED`，异常为 `FAIL`。历史页面直接展示这些状态。

## 数据流与错误处理

1. 创建任务时保存原始输入并标记 `PENDING`。
2. 加载结果后先完成现有 Pydantic/业务校验。
3. 校验成功：更新数据库状态、解析 JSON 和校验 JSON，再更新 checkpoint。
4. 校验失败：更新数据库状态为 `FAIL`，保存异常信息；不写入当前最终结果。
5. 若历史记录不存在，更新方法返回未更新结果并记录日志/提示，不创建无法关联的新历史记录。

## 测试

- 测试按 `run_id + stage` 更新成功。
- 测试不会更新其他阶段或其他运行。
- 测试 Stage 1/Stage 2 成功加载后的状态回写。
- 测试异常路径写入 `FAIL`。
- 保留现有测试并运行完整测试集。
