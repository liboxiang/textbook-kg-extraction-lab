# 教材知识单元（KU）拆分规则 V1.0

> 目标：将教材知识点（KP）拆分为可独立检索、可独立提问/考查、同时保留完整条件与上下文的原子知识单元（KU）。

> 核心口径：**原子不是“越短越好”，而是“最小完整语义”**。

## 一、底线原则

### P01｜语义原子，而不是句子原子

一个 KU 表达一个主要知识目标 / 一个可独立检索、提问或考查的完整语义单元。不能把“每句话、每个编号、每个顿号”机械当成 KU 边界。

- 推荐级别：必选
- 设计理由：进一步拆分会破坏语义完整性；与相邻内容合并又会引入第二个主要知识目标。

### P02｜最小完整语义原则

KU 要尽可能小，但必须完整保留主体、动作/结论、适用条件、数值阈值、单位、例外或限制条件。以“还能不能继续拆而不损失含义”判断原子性。

- 推荐级别：必选
- 设计理由：原子≠短。完整性优先于长度。

### P03｜原文有序完整覆盖

同一 KP 拆出的 KU 的 source_text 按 source_order 拼接后，应完整覆盖该 KP 原文；原则上不遗漏、不改写、不凭空补写。原文片段建议采用连续、非重叠 span。

- 推荐级别：必选
- 设计理由：保证可追溯、可重建、版本更新时可定位。

### P04｜原文与 AI 补充信息分离

KU 的 source_text 保存教材原文；AI 生成的 ku_title、摘要、关键词、内容要素、上下文补全等放独立字段，不混写进原文。

- 推荐级别：必选
- 设计理由：避免无法区分教材事实与模型生成内容。

### P05｜语义边界优先于排版边界

标题、（1）（2）、①②、换行、句号、分号只能作为候选边界；最终是否切开要看语义是否独立。

- 推荐级别：必选
- 设计理由：教材编号既可能列独立概念，也可能只是同一规则组的多个子项。

### P06｜上下文通过 metadata 继承，不靠重复原文

为每个 KU 保存 context_path（章/节/KP/小标题/阶段）和 kp_name。若原文出现“其、该、上述”等指代，可用 ku_title 或 context_summary 补全检索上下文，但不要篡改 source_text。

- 推荐级别：推荐
- 设计理由：既保证独立检索，又避免重复文本造成原文重建和版本比对困难。

## 二、按原文类型拆分

### T01｜定义 / 术语型

一个独立术语通常可形成一个 KU，保留“术语 + 定义 + 核心作用/特征”。多个并列术语如果每个都有独立定义，可分别拆；如果只是无解释的短名单，则保留为一个分类 KU。

- 推荐级别：推荐
- 设计理由：例如净跨径、计算跨径等适合按术语拆；纯名称枚举不宜拆成大量超短片段。

### T02｜组成 / 构成 / 作用型

先保留“整体由哪些部分组成”的总述为一个 KU；若各组成部分有独立定义、作用或要求，再按“一个部件 + 其完整作用/定义”拆分。

- 推荐级别：推荐
- 设计理由：总览适合整体召回，部件 KU 适合精确召回，两者语义目标不同。

### T03｜分类 / 类型型

先识别分类维度。若各类型带独立定义、特点或适用条件，可按“分类维度 + 某一类型 + 说明”拆分；若只是若干名称构成的短列表，则整个列表保留为一个 KU。

- 推荐级别：推荐
- 设计理由：拆分后必须能知道“按什么维度分类”，不能只剩一个孤立类型名。

### T04｜适用条件 / 判定条件型

一个 KU 应保留“对象 + 适用条件 + 全部必要阈值”。多条件共同决定一个结论时必须放在一起；不同对象的条件可分开。

- 推荐级别：推荐
- 设计理由：条件被拆散后会造成错误适用或错误检索。

### T05｜施工要求 / 规范要求型

不要默认“一条编号 = 一个 KU”。先按对象、施工阶段、动作或控制目标聚类；同一对象下连续的若干短要求可合为一个 KU，只有当某条要求可以独立提问且包含完整条件时才单独拆。

- 推荐级别：推荐
- 设计理由：这是本章最常见的文本类型，也是最容易过拆的类型。

### T06｜工艺流程 / 顺序型

完整流程链（A→B→C→…）默认作为一个 KU，不按每个步骤切碎。若教材随后详细解释某一步骤，可将“该步骤的详细要求”另拆 KU。

- 推荐级别：必选
- 设计理由：流程顺序本身就是知识，切成单步会丢失前后依赖。

### T07｜数值 / 阈值 / 公式型

数值必须与对象、条件、单位和比较关系一起保留。不得把“条件”与“数值”拆开，也不得把公式变量说明与公式主体拆开。

- 推荐级别：必选
- 设计理由：例如“设计无规定时，不低于设计强度的75%”必须整体保留。

### T08｜正向规则 + 例外 / 禁止型

若“允许/应当”与“但/除外/不得/设计无规定时”等共同限定同一行为，应放在同一 KU；只有例外本身能独立成立时才拆。

- 推荐级别：推荐
- 设计理由：避免只召回一般规则而漏掉关键例外。

### T09｜因果 / 目的 / 机理型

原因、措施与结果构成同一个解释链时不要拆开。例如“为什么这样做”与“这样做达到什么目的”应形成一个完整 KU。

- 推荐级别：推荐
- 设计理由：适合解释题、原理题和 Agent 推理。

### T10｜安全 / 质量控制型

优先按控制阶段或控制对象拆，例如“施工前、施工中、拆除阶段”或“材料、安装、检测”。同一阶段内的短规则可成组保留。

- 推荐级别：推荐
- 设计理由：比逐条编号拆分更符合业务问法，也减少超短 KU。

### T11｜表格 / 对照矩阵型

表格默认按一个完整语义矩阵保留，尤其是“类型—适用条件”“对象—指标—限值”这类对照关系。不要按单元格拆。若表格过大，可按逻辑行组拆，但每个分片必须重复/继承表头语义。

- 推荐级别：推荐
- 设计理由：表头与行列关系是知识的一部分；单元格脱离表头通常无法独立理解。

### T12｜规范引用 / 交叉引用型

“应符合某规范”“详见某节”等引用句原则上附着在它所限定的规则 KU 中，不单独形成只有引用信息的 KU。

- 推荐级别：推荐
- 设计理由：纯引用片段检索价值低，且缺少实际知识内容。

## 三、防止拆分过细

### G01｜禁止按标点机械切分

不得按句号、分号、冒号、顿号自动拆 KU。标点仅用于识别候选语义片段。

- 推荐级别：必选
- 设计理由：同一句或同一条中常同时包含条件、动作、阈值和例外。

### G02｜禁止把依赖上文的片段单独成 KU

若片段含“其、该、上述、其中、前者、后者、本项、此时”等强指代，且离开上文无法理解，则与前文合并，或仅通过 metadata 补全后再独立。

- 推荐级别：必选
- 设计理由：避免向量检索命中后仍不知道主体是谁。

### G03｜短并列规则优先成组

同一小标题、同一对象、同一阶段下的多个短要求，如果每条都只有一个简单属性或动作，优先合并成一个规则组 KU，而不是逐条拆。

- 推荐级别：推荐
- 设计理由：围堰一般要求、简短安全措施等尤其适用。

### G04｜比较关系必须成对保留

A 与 B 的差异、强弱、前后、正反条件需要放在同一 KU；不要只保留比较的一侧。

- 推荐级别：推荐
- 设计理由：比较知识被拆开后很难回答“区别是什么”。

## 四、防止 KU 过大

### L01｜出现多个独立知识目标时必须拆

同一片段如果同时讲“定义 + 分类 + 施工流程 + 质量验收”等多个独立目标，应按目标拆分，即使教材放在同一个 KP 中。

- 推荐级别：必选
- 设计理由：一个 KU 只保留一个主要知识目标。

### L02｜跨阶段时按阶段拆

文本明显跨越准备、制作、安装、浇筑、养护、拆除、验收等施工阶段时，优先以阶段为一级边界；流程总链除外。

- 推荐级别：推荐
- 设计理由：阶段通常对应稳定的业务问法和检索意图。

### L03｜跨对象时按对象拆

同一段连续讨论不同对象，如钢筋、模板、混凝土、支座，且各自具有完整规则，应按对象拆分。

- 推荐级别：推荐
- 设计理由：减少一个向量中混入多个主题。

### L04｜软长度上限

超过设定软上限时必须重新检查是否包含多个小标题、对象、阶段或知识目标；若仍是不可分割的完整表格/流程/长规则组，可以保留。

- 推荐级别：可选
- 设计理由：只做复检触发器，不强制按字数截断。

## 五、KU 结果校验

### V01｜独立可问性测试

给这个 KU 单独生成一个问题，若无需依赖相邻 KU 就能理解问题并回答，则通过；否则合并或补 context metadata。

- 推荐级别：必选
- 设计理由：直接检验检索后是否可用。

### V02｜继续拆分测试

尝试把 KU 再拆成两块；如果任一块会失去主体、条件、顺序、比较、因果或限制关系，则当前粒度已经足够原子。

- 推荐级别：必选
- 设计理由：防止为了“原子”而过拆。

### V03｜相邻合并测试

尝试与前后 KU 合并；如果合并后出现第二个独立知识目标、不同对象或不同阶段，则应维持拆分。

- 推荐级别：必选
- 设计理由：防止 KU 过大。

### V04｜原文覆盖校验

校验所有 source_span 是否按顺序覆盖整个 KP：无遗漏、无错序；若采用非重叠模式则同时检查无重叠。

- 推荐级别：必选
- 设计理由：这是自动化拆分上线前必须做的工程校验。

### V05｜标题可命名性测试

每个 KU 应能生成一个短而具体的 ku_title；如果标题只能写成“其他要求”“补充说明”“第二点”，说明该 KU 可能缺乏独立语义。

- 推荐级别：推荐
- 设计理由：标题是判断语义边界是否清晰的低成本信号。

## 长度护栏（仅用于报警 / 复检）

- 常规 KU 建议区间：约 **80–350** 字，仅供参考。
- 超过 **500** 字：触发“是否包含多个知识目标/对象/阶段”复检。
- 表格、流程链、不可分割的规则组不受字数硬限制；**严禁按字符数截断原文**。

## 推荐拆分流程

1. 读取完整 KP 原文，并识别章/节/KP/小标题/编号层级。
2. 将局部文本标注为：定义、组成、分类、适用条件、流程、施工要求、参数阈值、安全/质量控制、表格等类型。
3. 依据所选规则产生候选 KU 边界，排版编号只作为候选提示。
4. 合并失去主体/条件/上下文的过细片段。
5. 拆开包含多个独立知识目标、多个对象或多个阶段的过大片段。
6. 执行独立可问性、继续拆分、相邻合并、原文覆盖四项校验。
7. 最终只输出 KU 边界、主题、统领问题、章节路径及拆分证据；原文内容通过 block_id 范围回溯。

## 输出格式要求

模型执行拆分时，**只输出合法 JSON 对象，不输出 Markdown、解释、前后缀、代码围栏或其他文本**。

输出结构固定如下：

```json
{
  "knowledge_units": [
    {
      "temp_ku_id": "KU_01",
      "order_index": 1,
      "title": "完整论述模块的当前主题",
      "main_question": "统领该模块完整结果的专业问题？",
      "section_path": ["上位章节", "当前主题"],
      "start_block_id": "S0001",
      "end_block_id": "S0005"
    }
  ],
  "evidence": {
    "ku_split": [
      {
        "temp_ku_id": "KU_01",
        "evidence": "该范围围绕……形成完整结果；与相邻内容之间……，因此合并或形成边界。"
      }
    ]
  }
}
```

### 字段约束

- **temp_ku_id**：从 KU_01 开始按拆分顺序连续编号，不跳号、不重复。
- **order_index**：从 1 开始递增，必须与 temp_ku_id 顺序一致。
- **title**：概括该 KU 所覆盖完整论述模块的当前主题；不得写成“其他要求”“补充说明”“第几条”等无语义标题。
- **main_question**：用一个专业问题统领该 KU 的完整知识结果。问题必须能被该 KU 覆盖范围完整回答，不能只对应其中某一句或某个参数。
- **section_path**：按教材层级填写，从上位章节逐级到当前主题；不得凭空生成教材中不存在的业务分类。
- **start_block_id / end_block_id**：标记该 KU 在输入块序列中的连续起止范围。一个 KU 必须覆盖连续 block，不允许跨块跳跃拼接。
- **evidence.ku_split**：必须与 knowledge_units 一一对应，使用相同 temp_ku_id，说明“为什么这些 block 应合并为一个完整 KU，以及为什么在边界处应切开”。

### JSON 合法性约束

1. 只能输出一个 JSON 根对象。
2. 不允许输出 Markdown 代码围栏、解释文字、注释、尾随逗号或 JSON 之外的任何字符。
3. knowledge_units 与 evidence.ku_split 中的 temp_ku_id 必须完全一致、一一对应。
4. knowledge_units 必须按原文顺序排列，order_index 连续递增。
5. 每个 KU 必须使用连续 block 范围；前后 KU 不得交叉，不得倒序，不得遗漏输入 block。
6. 除非输入明确允许，否则不同 KU 的 block 范围不得重叠。
7. title、main_question、evidence 均为字符串；section_path 必须为字符串数组；order_index 必须为整数。
8. 不增加未定义字段；若无特殊要求，严格按照上述结构输出。

## 最终验收口径

一个合格 KU 应同时满足：**单一主要知识目标、完整论述闭环、条件与阈值完整、main_question 能被当前范围完整回答、block 范围连续且无遗漏、进一步拆分会损失含义、与相邻 KU 合并会引入新的知识目标。**
